# YouTube Playables readiness — standalone release assessment

Reviewed against the official English documentation on **2026-09-24**. The game at https://water-hole.vercel.app/ is a standalone browser release. This local gameplay revision has **not** been deployed. Neither build is a YouTube submission or certified Playable. No interest form, account action or upload was performed.

## Access and publication sequence

1. Developer access is still described as early access. If you have not been onboarded, use the interest form linked from the [official Playables home page](https://developers.google.com/youtube/gaming/playables) yourself, or contact your existing YouTube partner contact. Expressing interest does not guarantee acceptance.
2. Confirm that your channel has been onboarded and your account has channel manager permission. The [portal guide](https://developers.google.com/youtube/gaming/playables/developer_portal) describes invitation-only private preview. Signing into an ordinary YouTube channel or deploying on Vercel does not establish this access.
3. After integration and local testing, create a game draft, supply metadata/thumbnails, upload the ZIP, and create a release. Use its **Verify and test** development and Test Suite links on desktop web, mobile web, Android and iOS. Keep development links within certification testing.
4. Resolve failures before **Submit for Certification**. Follow the partner contact's release process. The [certification overview](https://developers.google.com/youtube/gaming/playables/certification/requirements) also requires accessibility, localization, privacy, content and other policy review; passing local gameplay tests is insufficient.

## Why the SDK adapter is deferred

This is more than replacing storage methods. Inspection of installed Phaser 3.90's `src/core/VisibilityHandler.js` and `Game.js` found independent document visibility and window focus handlers. The current adapter exposes only a pause callback; it has no host resume permission, readiness, audio gate or full-execution suspension contract. A storage-only adapter would leave those failures hidden. The focused gameplay revision therefore keeps the working standalone platform and documents a separate integration implementation instead of shipping an unverified partial SDK mode.

The official [integration requirements](https://developers.google.com/youtube/gaming/playables/certification/requirements_integration) require SDK-only lifecycle signals, suspension of all execution/rendering/interactions on host pause, host-controlled audio permission, and successful cloud loading before saving. Our implementation plan:

1. **Boot/build (`index.html`, `vite.config.ts`, `main.ts`):** introduce an explicit Playables build target with the SDK script before the game module; output to a separate directory. Keep the standalone bundle free of SDK requests. Mount a visible loading shell, signal its first frame, then enable the scene/UI only after initialization and signal interactive readiness exactly once. Handle zero-height initial frames and SDK-load failure visibly.
2. **Platform (`platform.ts`, new `youtube-platform.ts`):** define initialization, readiness, host pause/resume and audio-change subscriptions plus cleanup. Choose the platform explicitly at boot; use `IN_PLAYABLES_ENV` as validation, not a silent switch to localStorage when a submission cannot load its SDK.
3. **Lifecycle (`main.ts`, `game.ts`, `ui.ts`):** separate `userPaused` and `hostPaused`. On host pause clear input, suspend Web Audio, freeze engine updates/rendering, cancel or suspend UI timeouts/animations, and block DOM actions including Start/Replay/Resume/Mute. Only the SDK resume event may remove the host gate; a prior user pause must remain. Audit/disable Phaser's own visibility hooks using a maintained Playables engine entry or narrowly scoped build alias for its visibility module; do not monkey-patch global browser APIs. Verify there is no focus event that wakes a host-paused engine. Exclude suspended time from the 90-second clock.
4. **Audio (`audio.ts`):** add independent `hostAudioEnabled`; effective playback requires host permission, local preference, an active scene and an unlocked AudioContext. Apply both initial `isAudioEnabled()` and `onAudioEnabledChange`. Test host mute arriving during scheduled finish notes, focus changes and a user unmute.
5. **Save (`youtube-platform.ts`, `game.ts`):** await `loadData()`, parse `{version:1,best:<nonnegative safe integer>}`, then merge the maximum loaded/session best. Serialize writes so old requests cannot overwrite a newer best. Save new bests at the round boundary; flush current progress before host suspension as allowed by the lifecycle. If load fails, offer retry/unsaved play without calling `saveData`; if unknown future data appears, avoid destructive overwrite. Show save failure rather than claiming a persistent personal best. Keep load/save retry work suspended during host pause. Optional `sendScore({value:best})` follows a successful matching best save; omitting leaderboard reporting is also valid.
6. **Verification:** local adapter tests for event ordering, duplicate callbacks, load rejection/corrupt/old data, delayed loads, failed/concurrent saves, muted startup and user pause plus host pause. Browser checks must count actual render/update calls while paused and attempt all UI/keyboard resume paths. Then run the real SDK suite, CSP, network inventory and actual YouTube development links on phones. Mock tests alone do not establish certification.
